## 三、遗留与纪律

### 遗留（如实记录，不掩饰）

| 项 | 说明 |
|---|---|
| 转码吞吐持平 | 阶段 A 之前实测：24 任务 38505 ms，改造前 37897 ms。参数扫描证明是纯 CPU 瓶颈，调整线程分配无收益 —— 这不是本次改造的目标，故不追 |
| 去重竞态未复现 | 20 并发提交同一文件未复现重复入队（窗口极窄）。机制上三步非原子确实存在，已用 `inFlight.add()` 消除，**不依赖复现** |
| push 依赖代理 | `github.com:443` 直连不通，需 Clash 代理在运行 |

### 不可动摇的纪律

1. **先存基线，再改代码** —— 代码一改，改前现场就回不来
2. **每一小步留提交**，message 含「问题 → 改动 → 实测」
3. **别动包名与 `@author`** —— 会产生几万行 diff，把优化改动彻底淹没
4. **不破坏「零配置可启动」** —— 加中间件必须可降级
5. 讲并发线**只说 2 个线程池**；讲 SQL 线**绝不提 SQL 注入**（值全是 `?` 占位符，是伪问题）
6. 每条改造**附实测前后对比**，否则等于没做
